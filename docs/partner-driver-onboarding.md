# Partner driver onboarding

Partner owners/admins register a new driver from Partner workspace → Fleet → Add driver. They enter name, email and Ethiopian mobile phone. The backend creates an organization-scoped invitation and audit event, not an approved account. The Partner shares the private seven-day registration link with that driver; the application does not send messages automatically.

The driver opens the link, uses the registered email/phone, and sets their own six-digit driver PIN. An isolated Supabase client preserves the Partner's current browser session. Contact details are checked against the private invitation before signup; validation returns only a boolean. Email confirmation, when enabled, must finish before claiming organization membership. The driver returns to the same link and signs in after confirmation.

Claiming requires a matching confirmed Auth email, matching profile phone, a new pending Driver profile created after the invitation, an active organization, and an unexpired invitation. Existing HALLO accounts and existing fleet ownership cannot be claimed. Duplicate emails require explicit HALLO review, rather than automatic ownership transfer. No #508/#514 accounts are copied into production.

Partner workspace lists its own registrations and driver approval status. Admin Partner driver review can explicitly link an unassigned canonical truck from that same Partner for document onboarding. Other drivers, other organizations, maintenance/suspended vehicles, existing other vehicle ownership and active trips are protected. Pending drivers and their linked fleet vehicle remain inactive. This avoids the old HALLO onboarding link, which deliberately excludes Partner fleet vehicles, without changing that HALLO flow.

Admin Partner driver review links to the existing document compliance page for document verification. Partner review approves the organization registration and calls the existing driver onboarding approval function in one transaction. Missing/expired identity or vehicle documents roll back both changes. A narrow profile trigger prevents registered Partner drivers from bypassing this approval through the generic HALLO approval path; drivers without a claimed Partner registration are unchanged. A review reason and immutable Partner activity event are recorded. Registration itself never assigns a vehicle or approves work automatically.

The new table has RLS and a deny-all direct-access policy, with no anonymous/authenticated table grants. Organization management and review RPCs are authenticated and server-authorized. The only anonymous RPC validates supplied contact details against an unpredictable private invitation token; it returns no recipient details, grants no membership, and changes no data. Tokens are returned only to authorized organization managers through the listing RPC.

Deployment: the standalone Partner/Admin app includes registration, review and existing driver document review routes. The full app gets the new routes as well, but its production migration parity blocker remains separate. Preserve Vercel access protection: owner-controlled smoke can use the protected deployment; general driver access requires the approved public production release/domain. Do not describe a protected smoke URL as a public driver rollout.

Verification: executable PGlite tests exercise organization/role isolation, duplicate/existing account guards, matching contact validation, self-claim and safe retries, pending status, leadership review, approval prerequisites, expired links, suspended organizations and ACLs. The browser test uses the actual UI and Supabase SDK, with Auth/RPC HTTP boundaries replaced; it checks recipient validation before signup, preserved Partner browser session and approval controls. A production rollback smoke must leave no registration or activity fixtures behind. Device signup/email confirmation, document upload and Admin review remain owner checks after deployment.
